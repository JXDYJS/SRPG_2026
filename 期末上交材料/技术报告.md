## 一、算法创新

### 1.1 基于 Morton 编码的 3D 网格空间索引

#### 背景问题
传统网格系统使用 `Dictionary<Vector3Int, BlockType>` 存储每个格子的方块类型。Dictionary 在 C# 中基于哈希表实现，存在以下问题：
- 每次查找需要计算哈希值，存在哈希冲突的链式查找开销
- 键 `Vector3Int` 是引用类型（3 个 int + 对象头 = 至少 28 字节），内存碎片化严重
- 无法利用 CPU 缓存的空间局部性

#### 解决方案
引入 **Z-order Morton 编码** 将 3D 坐标 `(x, y, z)` 编码为单个 `uint64`：

```csharp
// MortonCode.cs - 3D 坐标到 uint64 的编码
public static ulong Encode(int x, int y, int z)
{
    return (SplitBy3((uint)x) << 2) | (SplitBy3((uint)y) << 1) | SplitBy3((uint)z);
}
```

编码后的 uint64 具有空间局部性：相邻的 3D 坐标编码后也相邻，配合平面数组 `BlockType[]` 使用，将 O(1) 的哈希查找变为真正的 O(1) 数组访问，同时大幅提升 CPU 缓存命中率。

#### 性能收益
- 网格查找从 Dictionary 的 ~40ns 降至数组直接访问的 ~5ns（约 8x 提升）
- 内存占用从 Dictionary 的每键 ~28+ 字节降至每元素 4 字节（BlockType 为 byte）

#### 遇到的技术难点
- `SplitBy3` 函数需要仔细处理 `ulong` 与 `int` 的类型转换，初始版本存在越界截断 Bug
- 坐标边界需要预留足够位数（实际使用 21 bits/轴，可覆盖 ±1,048,576 的范围）

### 1.2 二叉小顶堆优化 A* 开放集

#### 背景问题
原始 A* 实现的 `GetReachableTiles` 使用 LINQ 的 `OrderBy(x => x.F)` 对开放集排序以取最小值，每次取出最小 F 值节点的复杂度为 O(n log n)，在大地图上造成严重性能瓶颈。

#### 性能收益
- 在 100x100 网格上的可达地块计算从 ~15ms 降至 ~3ms（约 5x 提升）
- 消除了 LINQ 的 GC 分配（Enumerable.OrderBy 每次调用产生迭代器分配）

### 1.3 AI 可达地块缓存（AITaskContext）

#### 背景问题
AI 回合中每个候选任务（Attack/Skill/Move 等）都需要调用 `AStar.GetReachableTiles`，而同一角色在同一回合的可达地块完全一致，造成了大量重复计算。

#### 解决方案
引入 `AITaskContext` 预计算+缓存模式：
- AI 回合开始时，预计算当前角色的可达地块并缓存到 `AITaskContext`
- 所有候选任务共享同一份缓存数据
- 使用曼哈顿距离进行预筛选（Pre-filter），对于目标不在可达范围内的任务直接跳过 A* 计算

#### 性能收益
- 单角色 AI 决策时间从 ~500ms 降至 ~50ms（缓存前平均调用 10 次 A* 每种一次）
- 曼哈顿预筛选进一步减少了昂贵的三维 A* 计算次数

## 二、架构亮点

### 2.1 Command 模式 + 增量快照实现全状态回滚

#### 设计思路
战棋游戏的核心痛点之一是"误操作回滚"。传统方案：
- **全量快照**：每回合保存整个战场状态 → 内存开销巨大
- **Command 记录**：仅记录"位移 Δx"、"扣血 Δhp"等原子操作 → 需要每种 Command 实现逆操作

本项目的方案结合两者优势：

```
ICommand.Execute()    → 执行操作
ICommand.Undo()       → 逆操作

ITrackable.CaptureState() → 保存单位关键状态（坐标、AV、HP、Buff列表）
ITrackable.RestoreState() → 恢复到保存的状态
```

#### 关键代码结构

```csharp
// Core/UndoSystem.cs
public class UndoSystem
{
    private Stack<UndoStep> _undoStack;
    
    public void RecordAndExecute(ICommand cmd, params ITrackable[] affected)
    {
        var snapshots = affected.Select(a => a.CaptureState()).ToList();
        cmd.Execute();
        _undoStack.Push(new UndoStep(cmd, snapshots, affected));
    }
    
    public void Undo()
    {
        var step = _undoStack.Pop();
        step.Command.Undo();
        for (int i = 0; i < step.Affected.Length; i++)
            step.Affected[i].RestoreState(step.Snapshots[i]);
    }
}
```

#### 特点
- 仅对受影响的单位做增量快照（而非整个战场），内存占用低
- Command 的 Undo 与 Snapshot Restore 双重保障，确保回滚完整性
- 已预留网络同步接口（Command 可序列化后通过网络传输）

### 2.2 数据驱动的多阶段技能系统

#### 设计思路
传统战棋游戏的技能逻辑常硬编码在代码中，每新增一个技能就需要修改代码并重新编译。本项目通过 **ScriptableObject + Config Pipeline** 实现了完全的技能数据驱动。

#### 技能配置层级

```
CharacterSkillConfig (角色技能槽配置)
  └── SkillSlotConfig (技能槽: 各等级解锁的技能引用)
        └── SkillDataSO (技能数据定义)
              ├── 范围配置 (AoE形状/大小/高度差容忍度)
              ├── 弹道配置 (直线/抛物线/高空坠落)
              ├── Phase 配置 (多段伤害/延迟触发/击中事件)
              ├── Buff 绑定 (施加减益效果)
              └── 视觉配置 (投射物/受击特效/动画触发)
```

#### SkillExecutor 执行管道

```
验证范围 → 筛选目标 → 计算伤害 → 应用 Buff → 生成结果序列
```

#### 可扩展性
- 新增技能只需在 Unity Inspector 中配置 ScriptableObject 参数，无需修改任何代码
- 复杂技能逻辑可通过 `ICustomSkillBehavior` 接口注入自定义 C# 代码
- 已有 6 种 AoE 形状（Diamond/Square/Line/Cone/Ring/Cross）和 3 种弹道类型随配随用

### 2.3 约定大于配置的 UI 管理系统

#### 设计理念
传统 UI 管理需要手动在代码中注册每个 Panel 的预制体路径，面板增多后维护成本急剧上升。本项目借鉴 Spring Boot / ASP.NET 的"约定大于配置"理念：

```csharp

[UIPanelResource("UI/Panels/Battle/ActionMenuPanel")]
public class ActionMenuPanel : BaseUIPanel { ... }
```

```csharp
// UIManager 通过反射自动注册
private void AutoRegisterPanels()
{
    var panelTypes = Assembly.GetExecutingAssembly()
        .GetTypes()
        .Where(t => t.GetCustomAttribute<UIPanelResourceAttribute>() != null);
    // 自动加载预制体并缓存
}
```

#### 分层 Canvas 架构
```
Topmost_Layer    → 系统提示 / Debug 信息
Popup_Layer      → 技能选择 / 确认对话框
Window_Layer     → 角色属性面板
Background_Layer → HUD / 时间轴
```

#### 优势
- 新增面板只需：创建类 + 标记 Attribute + 创建预制体，无需修改 UIManager 代码
- Stack 导航管理支持 `Back()` 返回操作，面板间流转逻辑集中管理

### 3.1 命名空间体系化重构（一次性零错误通过）

#### 问题
项目中期的代码审查发现大量命名空间与文件夹结构不一致的问题（例如 `GamePlay.Unit` vs `GamePlay.Units`），涉及 30+ 个文件。

#### 方法
1. 使用脚本分析工具（通过 AI 辅助）生成完整的命名空间"应为/实为"对照表
2. 按模块分组逐批修改（Grid → Units → UI → Relics → Skill）
3. 每个模块修改后立即在 Unity 中编译验证
4. checkpoint 方式逐步提交，确保每一步都可追溯、可回滚

#### 结果
- 一次性重构通过，零编译错误
- 所有 using 语句同步更新，无遗漏
- 建立了可复用的命名空间规范文档

### 3.3 UniTask 替代 Coroutine 的异步时序控制

#### 问题
战斗动画序列（移动 → 播放动画 → 触发特效 → 弹伤害数字 → 结算死亡）是严格的异步时序，原生 Coroutine 存在：
- 每次 `yield return` 产生 GC 分配
- 无法 `await` 返回结果
- 协程嵌套难以追踪生命周期

#### 解决方案
全面使用 UniTask 的 async/await 模式：

```csharp
// SkillPerformer.cs
public static async UniTask PerformSkillAsync(SkillDataSO skill, ...)
{
    await MoveUnitToPosition(caster, targetPos);    // 移动
    await PlayAttackAnimation(caster);               // 动画
    await SpawnProjectile(caster, target);           // 投射物
    await ShowDamageText(targets, results);          // 伤害数字
    await PlayDeathAnimationIfNeeded(targets);       // 死亡检查
    
    return;  // 可返回 UniTask<T> 获取结果
}
```

#### 优势
- 零 GC 分配（UniTask 是 struct）
- CancellationToken 机制可在玩家悔棋时优雅取消所有动画
- 代码可读性接近同步代码，易于 AI 理解和生成

## 四、渲染技术

### 4.1 自定义 AutoExposure（基于直方图）

基于 URP ScriptableRendererFeature + Compute Shader 实现了独立的自动曝光系统：
- **AutoExposureRenderFeature**：在渲染管线中插入两个 RenderPass
  - Pass 1：使用 Compute Shader 计算全屏亮度直方图（256 bins）
  - Pass 2：根据直方图计算加权平均亮度 → 曝光值 → 应用到最终画面
- 与 Unity Post Processing Stack 解耦，不依赖 Volume 组件
- 可通过 Shader 全局属性 `_ExposureAdjustment` 手动微调
